# Архитектура CyberCheck

Документ отвечает на вопрос «как это устроено и почему именно так». Он не заменяет `README.md` (там запуск и переменные окружения) и `.github/SECURITY.md` (там порядок сообщения об уязвимостях).

**Кодовые ориентиры:** `src/server.js`, `src/checks.js`, `src/net-guard.js`, `public/script.js`, `test/net-guard.test.js` — пять файлов, около 600 строк вместе с тестами. Проект сознательно маленький.

> **Соглашение о ссылках.** Ссылки в этом документе указывают на **функции и уникальные комментарии-маркеры** в коде, а не на номера строк: номера устаревают от любой вставки строки или прогона форматтера, а имена — нет. Чтобы найти место, нажмите `Ctrl+F` и введите имя функции (`checkCooldown`, `isPublicIp`, `resolvePublicIps`) или текст маркера (`3. Сначала валидация`, `4. Лимит частоты`).

## 1. Назначение и границы

**Что делает:** по запросу `hostname` проверяет доступность пяти портов (`80, 443, 22, 3306, 8080`), читает TLS-сертификат на найденном веб-порту и наличие четырёх HTTP-заголовков безопасности. Возвращает отчёт в JSON, фронтенд рендерит его текстом.

**Чего не делает (границы):**

* не эксплуатирует уязвимости и не пытается аутентифицироваться на цели;
* не аутентифицирует пользователей — API публичный;
* не хранит результаты сканирований (ни БД, ни файлов, ни кэша);
* не проверяет, что домен принадлежит отправителю (галочка согласия — только фиксация намерения);
* не сканирует пути (`https://site/admin` будет проверен как `https://site/`).

Формулировка «не эксплуатирует» — не маркетинг: вся работа ограничена TCP-connect, TLS-хендшейком и чтением заголовков ответа. Тело ответа не скачивается: `res.destroy()` вызывается сразу после получения заголовков в обработчиках `http.get`/`https.get` внутри `checkHeaders()`.

## 2. Компоненты

```
┌──────────────┐
│   Браузер    │  public/index.html + script.js + style.css
│  (vanilla)   │  fetch("/api", ...)  ← относительный путь, тот же origin
└──────┬───────┘
       │ POST /api/scan {url, consent, consentTimestamp}
       ▼
┌─────────────────────────────────────────────────────────────┐
│ Express (src/server.js)                                     │
│  helmet ─→ cors ─→ express.json(8kb) ─→ express.static      │
│                              │                              │
│                              ▼                              │
│                    POST /api/scan                           │
│                    ├─ rateKey + cooldown   (in-memory Map)  │
│                    ├─ валидация входа                       │
│                    ├─ new URL() + hostRegex                 │
│                    └─ console.log (hostname, ip)            │
└──────────────────────────────┬──────────────────────────────┘
                               ▼
                  ┌──────────────────────────┐
                  │ src/net-guard.js         │
                  │ resolvePublicIps(host)   │ ── dns.lookup(all)
                  │  · все IP публичные?     │
                  │  · IPv4 — первым         │
                  └────────────┬─────────────┘
                               │ connectIp (IP, не hostname!)
                               ▼
                  ┌──────────────────────────┐
                  │ src/checks.js            │
                  │ checkPort ×5 (3 c)       │
                  │ checkSSL  (3 c)          │
                  │ checkHeaders (5+5 c)     │
                  └────────────┬─────────────┘
                               │ TCP / TLS / HTTP
                               ▼
                        ┌─────────────┐
                        │ Цель (сайт) │
                        └─────────────┘
```

**Ключевые модули и их ответственность:**

| Модуль | Отвечает за | Не отвечает за |
|---|---|---|
| `server.js` | HTTP-слой, лимит, валидация входа, сборка ответа, конфигурация | сетевые проверки |
| `net-guard.js` | решение «можно ли подключаться к этому хосту» | сам процесс подключения |
| `checks.js` | сетевые проверки и разбор их результатов | валидация ввода |
| `public/script.js` | UI, таймаут 30 с, рендер через `textContent` | любые решения о безопасности |

## 3. Путь запроса

| # | Шаг | Где искать | Что даёт |
|---|---|---|---|
| 1 | Валидация конфигурации (`PUBLIC_ORIGIN`) | `server.js` → маркер «1. Строгая проверка PUBLIC_ORIGIN» | парсинг URL + проверка схемы: сервер не стартует без валидного http(s)-origin |
| 2 | `TRUST_PROXY` | `server.js` → `app.set("trust proxy", …)` | модель доверия к `X-Forwarded-For` |
| 3 | Заголовки безопасности + CSP | `server.js` → `helmet({ … })` | XSS-защита в глубину, запрет фреймов (CSP и `X-Frame-Options: DENY` согласованы) |
| 4 | CORS с явным origin | `server.js` → `cors({ origin: [PUBLIC_ORIGIN] … })` | чужой сайт не сможет дёргать API из браузера |
| 5 | Разбор JSON, лимит 8 КБ | `server.js` → `express.json({ limit: "8kb" })` | защита от раздутых тел, 413 вместо стека |
| 6 | Статика | `server.js` → `express.static(…)` | отдаёт `public/` |
| 7 | Валидация: тип/длина `url`, `consent === true`, окно timestamp | `server.js` → маркер «3. Сначала валидация» | отсекает мусор до сети и до лимита |
| 8 | `new URL()` | `server.js` → `parsed = new URL(…)` | нормализация: octal/hex/decimal-формы IP схлопываются парсером |
| 9 | `hostRegex` | `server.js` → `hostRegex.test(hostname)` | отсечение IPv6-литералов, мусора, FQDN с точкой |
| 10 | Лимит частоты | `server.js` → маркер «4. Лимит частоты» → `checkCooldown(rateKey(ip))` | выдаётся только запросам, прошедшим шаги 7-9 |
| 11 | Лог | `server.js` → маркер «5. Логируем ПОСЛЕ валидации» | после всех проверок — лог-инъекция невозможна |
| 12 | `resolvePublicIps` | `net-guard.js` → `resolvePublicIps()` | решение об SSRF |
| 13 | 5 портов параллельно → SSL → заголовки | `server.js` → `Promise.all` + `checkSSL` / `checkHeaders` | собственно скан |
| 14 | Ответ или ошибка | `server.js` → `res.json(…)`, `catch` в обработчике, error handler | JSON, без внутренних деталей |

Бюджет времени: порты параллельно (≤3 с) + TLS (≤3 с) + HTTP (5 с, при ошибке ещё 5 с) ≈ до 16 с; клиентский таймаут — 30 с (`AbortController` + `setTimeout` в функции `scan()`, `public/script.js`), то есть с запасом. Ограничителя одновременных сканов нет — это одна из известных проблем, см. §12.

## 4. Модель доверия

| Субъект / данные | Доверяем? | Обоснование |
|---|---|---|
| `req.body` (url, consent, timestamp) | ❌ нет | валидируется; `consent` — только флаг намерения |
| `req.ip` | ⚠️ условно | при `TRUST_PROXY=0` — адрес сокета; при `>0` — значение `X-Forwarded-For`, доверять можно **только** если перед приложением реально стоит прокси |
| DNS-ответ резолвера | ❌ нет | проверяются **все** полученные адреса; при смешанном ответе — полный отказ |
| `connectIp` (результат проверки) | ✅ да | это и есть смысл схемы: подключаемся к тому, что проверили, а не к имени |
| Сертификат цели | ❌ нет | читается с `rejectUnauthorized:false`, валидность определяется по `authorizationError` |
| Заголовки ответа цели | ❌ нет | извлекается только `Server` и факт наличия 4 заголовков; значения не интерпретируются |
| Конфигурация (env) | ✅ да в пределах процесса | `PUBLIC_ORIGIN`, `TRUST_PROXY`, `DEMO_MODE`, `NODE_ENV`, `PORT` |

## 5. Ключевой инвариант SSRF-защиты

Схема держится на трёх шагах, и порядок здесь — часть защиты:

1. **Резолв**: `dns.lookup(hostname, { all: true })` — получаем **все** адреса.
2. **Проверка всех**: `if (!ips.every(isPublicIp)) return []` внутри `resolvePublicIps()` (`net-guard.js`) — если хотя бы один адрес не публичный, отказ целиком. Это защищает от «умного» DNS, который отдаёт публичный адрес для проверки и приватный для подключения.
3. **Подключение по проверенному IP**: `connectIp = resolvedIps[0]` в обработчике `POST /api/scan` (`server.js`), а hostname передаётся отдельно — в заголовке `Host` (оба вызова `http.get`/`https.get` внутри `checkHeaders()`) и в SNI через `servername` (`checkSSL()` и `checkHeaders()`).

**Почему это закрывает DNS rebinding:** между «проверили» и «подключились» нет повторного резолва. Даже если домен сменит A-запись через секунду после проверки, соединение пойдёт на уже проверенный IP. Классическая уязвимость — «проверили имя, подключились по имени» — здесь устранена конструктивно.

**Классификация адреса** (`isPublicIp()` в `net-guard.js`) построена как аллоулист: разрешено только `ipaddr.js.range() === "unicast"`. Всё остальное — приватное, loopback, link-local, CGNAT, ULA, multicast, 6to4, Teredo, NAT64 — блокируется по умолчанию. Нераспознанный ввод тоже блокируется (fail closed). Перед проверкой диапазона выполняются три разворачивания/исключения — они пронумерованы комментариями внутри самой функции: «1. Разворачиваем IPv4-mapped IPv6 любой формы», «2. Проверяем NAT64 (64:ff9b::/96)» с рекурсивной проверкой встроенного IPv4 и «3. Блокируем IPv4-compatible (::/96)».

**Чего эта схема не закрывает:**

* **NAT64/DNS64 с нестандартным префиксом.** Фильтр по литералу видит «обычный публичный IPv6», а сеть за ним маппит его во внутренний IPv4. Лечится только сетевым egress-фильтром.
* **Любую цель, которая действительно публична.** Сканирование публичного чужого хоста защитой не блокируется — это вопрос назначения сервиса и правовой, а не технический.

## 6. Демо-режим и принцип fail-closed

`DEMO_MODE=true` разрешает обойти проверку и обратиться к `localhost` / `127.0.0.1` — это ветка `if (DEMO_MODE && (hostname === "localhost" …))` в обработчике `POST /api/scan`. Это единственная ветка, обходящая SSRF-фильтр, поэтому её включение защищено двумя условиями — они стоят в блоке проверки конфигурации в самом начале `server.js`:

```
DEMO_MODE === "true"  И  NODE_ENV === "development"   →  работаем
иначе (если DEMO_MODE)                                 →  process.exit(1)
```

Логика специально инвертирована: раньше проверка была «если production — запретить», то есть при незаданном `NODE_ENV` (значение по умолчанию в любом голом окружении) демо-режим молча включался. Теперь «разрешено только при явно заданном development» — ошибка конфигурации не открывает доступ, а останавливает сервис. Формулировка «запрещено по умолчанию» — это и есть fail-closed.

## 7. Лимит частоты

```
rateKey(req.ip) → IPv4-mapped разворачивается до IPv4
                → IPv6 нормализуется до /64 (смена младших 64 бит не даёт нового окна)
                → невалидный адрес → общий бакет "unknown"
                    ↓
lastScan: Map<key, timestamp>   TTL = 10 с, чистка раз в 30 с, MAX_KEYS = 10 000
                                вытеснение — LRU (ключ при касании переносится в конец)
```

Лимит списывается **после** валидации и проверки hostname (вызов `checkCooldown(rateKey(ip))` в обработчике `POST /api/scan`), поэтому ни мусорные тела, ни подделанное согласие, ни невалидные имена окно не занимают. Вытеснение — LRU в функции `remember()`: активный ключ при обращении переносится в конец очереди и не выпадает первым. Невалидный адрес клиента не создаёт отдельный бакет, а попадает в общий `"unknown"` — этот `return` в конце `rateKey()` нужен затем, чтобы смена `X-Forwarded-For` не давала бесконечного числа окон.

Смысл `/64`-нормализации: без неё клиент с одной IPv6-подсетью получает 2⁶⁴ бесплатных окон. С ней окно одно на подсеть — но, следовательно, **соседи по подсети делят его между собой** (осознанный компромисс).

Что лимит **не** обещает:

* не защищает от источника с выделенной `/48` (65 536 подсетей `/64`) или от ботнета;
* не является глобальным — карта живёт в памяти процесса, поэтому N реплик = N лимитов;
* **не ограничивает запросы, отвалившиеся на валидации** (маркер «3. Сначала валидация» и `hostRegex` в `server.js`): лимит стоит после неё, поэтому поток невалидных `url`/hostname — бесплатный канал без cooldown. Компромисс осознанный (иначе опечатка стоила бы 10 секунд), но для публичного сервиса нужен второй, «широкий» лимит на все запросы к `/api/scan`;
* уязвим к неверной настройке `TRUST_PROXY` — при `>0` без реального прокси значение `req.ip` приходит из заголовка, который контролирует клиент.

Для публичного развёртывания нужен внешний лимит (`express-rate-limit` + Redis), это прямо написано в README.

## 8. Обработка ошибок

Единый обработчик — `app.use((err, req, res, next) => …)`, последний middleware перед `/healthz`. В нём: статус берётся из `err.status`/`err.statusCode`, в лог пишутся метод, путь и стек (два вызова `console.error`), а наружу — дифференцированный текст в переменной `message`, чтобы 5xx не выдавалась за ошибку клиента. Через него проходят:

* ошибки `express.json()` — битый JSON (400), слишком большое тело (413);
* синхронные исключения маршрута;
* всё, что делает `next(err)`.

Наружу уходит только `{ error: <обобщённый текст> }` — без стека, без путей, без версий библиотек. Принципиальный момент: **это не зависит от `NODE_ENV`**. Раньше защита держалась на переменной окружения (не задал production — получил стек в ответе), теперь она работает всегда, а `NODE_ENV` влияет лишь на текст 404 от `finalhandler`.

Внутри маршрута свой `catch` логирует исключение и отдаёт обобщённый 500. Диагностика при этом не потеряна: стек остаётся в серверном логе и не уходит клиенту. Остаточный путь утечки — `if (res.headersSent) return next(err)` в конце error handler: ошибку добирает `finalhandler`, который в не-production окружении умеет вернуть стек. Практически недостижимо, но именно поэтому `NODE_ENV=production` на проде всё ещё имеет смысл.

## 9. Фронтенд и CSP

* `API_URL = "/api"` — относительный путь. Поэтому одинаково работает `http://localhost:3000`, LAN-адрес и HTTPS за прокси, и не конфликтует с собственной политикой `default-src 'self'` (из которой наследуется `connect-src`).
* Рендер — **только** `textContent`. Причина не в аккуратности: в отчёт попадает `Server`-заголовок чужого сервера, то есть данные, контролируемые третьей стороной. `innerHTML` здесь был бы XSS.
* Обработчик кнопки вынесен из разметки — `addEventListener("click", scan)` в конце `public/script.js`, — чтобы работал строгий `script-src 'self'` без `'unsafe-inline'`.
* `style-src` сужен до `'self'` — инлайновых стилей в разметке нет.
* `X-Frame-Options` выставлен явно в `DENY` (`xFrameOptions: { action: "deny" }` в конфиге `helmet`), чтобы legacy-заголовок не расходился с `frame-ancestors 'none'`: по умолчанию helmet отдаёт `SAMEORIGIN`, а расхождение между двумя механизмами защиты от фрейминга — плохой сигнал для читателя.
* Клиентский таймаут (30 с) реализован через `AbortController`, кнопка блокируется на время запроса.

## 10. Что сервер хранит и логирует

| Данные | Где | Срок жизни |
|---|---|---|
| IP клиента | `lastScan` (память) | ≤10 с, при переполнении вытесняется |
| IP клиента | `console.log` | навсегда — в stdout/логах процесса; ротации нет |
| hostname цели | `console.log` | то же |
| Результаты скана | только в HTTP-ответе | не сохраняются |
| Сертификаты, заголовки цели | только в ответе | не сохраняются |
| Секреты, токены, пароли | — | отсутствуют: внешних API проект не вызывает |

Ничего не пишется на диск. Единственное состояние процесса — `Map` со временами последних запросов.

При старте в лог попадает разрешённый origin и, если включён демо-режим, соответствующая строка — оба `console.log` находятся в колбэке `app.listen`. Это диагностика, а не секрет: origin и так виден в заголовках. Есть отдельный маршрут `app.get("/healthz", …)`, который отдаёт `{ok, uptime}` — ничего сверх факта, что сервис жив.

## 11. Тестирование

Покрыто: `test/net-guard.test.js` — 20 адресов на блокировку (включая `::ffff:7f00:1`, `::127.0.0.1`, `64:ff9b::7f00:1`, `::7f00:1` и `::a9fe:a9fe`), 4 на разрешение и 5 мусорных на fail-closed. Ключевые развороты — mapped, NAT64 и запрет `::/96` — закреплены тестами, то есть ровно те адреса, которые закрывали дыры аудита v3, теперь защищены от регрессии. Классификация адресов — единственное решение, на котором держится SSRF-защита, и она проверяется без сети.

Не покрыто и почему:

| Что | Почему нет | Как закрыть |
|---|---|---|
| `resolvePublicIps` | `dns.lookup` вшит внутрь функции | инъекция резолвера: `resolvePublicIps(host, { lookup = dns.lookup } = {})` → три теста (все публичные / смесь / только IPv6) |
| `rateKey` | не экспортируется | экспорт + тесты на `/64`-группировку, IPv4-mapped и бакет `"unknown"` |
| `remember` / LRU-вытеснение | не экспортируется | вынести в модуль и проверить, что при переполнении вытесняется самый давно использованный ключ, а не самый старый по вставке |
| HTTP-слой (400 без стека, 429, CORS-заголовок) | `server.js` делает `process.exit()` и `app.listen()` при импорте — импортировать нельзя | разделить `src/app.js` (экспорт приложения) и `src/server.js` (env + listen) |
| `checks.js` | требует сети | `parseHeaders` — чистая функция, тестируется без сети |

## 12. Технический долг

| Долг | Влияние |
|---|---|
| `server.js` выполняет `process.exit()` в проверках конфигурации (`PUBLIC_ORIGIN`, `DEMO_MODE`) и вызывает `app.listen()` при загрузке модуля | HTTP-слой непокрываем тестами (см. §11) |
| Конфигурация размазана по началу `server.js` (`PUBLIC_ORIGIN`, `DEMO_MODE`, `TRUST_PROXY`, `PORT`) | нет единой валидации env; `PORT=abc` уйдёт в `listen("abc")` и создаст unix-socket вместо порта |
| Лимит стоит после валидации | поток невалидных запросов не ограничен ничем — для публичного сервиса нужен второй, широкий лимит (см. §7) |
| Нет потолка одновременных сканов | при обходе лимита — исчерпание дескрипторов; частично сглажено тем, что лимит срабатывает до сети |
| Express 4 | самая свежая в линии 4.x и получает патчи; переход на 5.x — отдельная задача |
| Нет `engines`, `private: true` в `package.json` | случайный `npm publish`; расхождение версий Node между локалью и CI |

## 13. Модель угроз (кратко)

| Угроза | Контроль | Остаток |
|---|---|---|
| SSRF к внутренней сети / metadata | резолв + проверка всех IP + подключение по IP; запрет `::/96` | NAT64/DNS64 с нестандартным префиксом |
| DNS rebinding | подключение по проверенному IP, без повторного резолва | — |
| XSS через данные цели | `textContent`, строгий CSP, вынесенный обработчик | — |
| Утечка внутренней информации через ошибки | единый error handler, JSON без деталей, стек только в серверный лог | `next(err)` при `headersSent` → `finalhandler` (в dev вернёт стек) |
| Подмена `X-Forwarded-For` при неверном `TRUST_PROXY` | невалидные значения схлопываются в общий бакет `"unknown"`, IPv6 — в `/64` | включать `TRUST_PROXY` только за реальным прокси |
| Использование сервиса третьими лицами | CORS по origin, лимит частоты, согласие, DISCLAIMER | распределённый источник; нет проверки владения доменом |
| DoS на сам сервис | лимит по `/64` с LRU-вытеснением, `MAX_KEYS`, таймауты 3-5 с | нет потолка параллельных сканов; невалидные запросы не лимитируются; лимит обходится распределённым источником |
| Захват зависимости | `npm ci`, lock-файл с `integrity`, `contents: read`, `npm audit --audit-level=high` и `timeout-minutes` в CI | Actions закреплены тегами, а не по SHA |
| Утечка секретов | секретов нет; `.env` в `.gitignore` | — |
