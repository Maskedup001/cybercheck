# Архитектура CyberCheck

Документ отвечает на вопрос «как это устроено и почему именно так». Он не заменяет `README.md` (там запуск и переменные окружения) и `.github/SECURITY.md` (там порядок сообщения об уязвимостях).

**Кодовые ориентиры:** `src/server.js` (206 строк), `src/checks.js` (145), `src/net-guard.js` (75), `public/script.js` (100), `test/net-guard.test.js` (55). Всего ~580 строк вместе с тестами (около 525 без них) — проект сознательно маленький.

---

## 1. Назначение и границы

**Что делает:** по запросу `hostname` проверяет доступность пяти портов (`80, 443, 22, 3306, 8080`), читает TLS-сертификат на найденном веб-порту и наличие четырёх HTTP-заголовков безопасности. Возвращает отчёт в JSON, фронтенд рендерит его текстом.

**Чего не делает (границы):**

* не эксплуатирует уязвимости и не пытается аутентифицироваться на цели;
* не аутентифицирует пользователей — API публичный;
* не хранит результаты сканирований (ни БД, ни файлов, ни кэша);
* не проверяет, что домен принадлежит отправителю (галочка согласия — только фиксация намерения);
* не сканирует пути (`https://site/admin` будет проверен как `https://site/`).

Формулировка «не эксплуатирует» — не маркетинг: вся работа ограничена TCP-connect, TLS-хендшейком и чтением заголовков ответа. Тело ответа не скачивается (`res.destroy()` сразу после получения заголовков, `checks.js:93, 117`).

## 4. Модель доверия

| Субъект / данные | Доверяем? | Обоснование |
|---|---|---|
| `req.body` (url, consent, timestamp) | ❌ нет | валидируется; `consent` — только флаг намерения |
| `req.ip` | ⚠️ условно | при `TRUST_PROXY=0` — адрес сокета; при `>0` — значение `X-Forwarded-For`, доверять можно **только** если перед приложением реально стоит прокси |
| DNS-ответ резолвера | ❌ нет | проверяются **все** полученные адреса; при смешанном ответе — полный отказ |
| `connectIp` (результат проверки) | ✅ да | это и есть смысл схемы: подключаемся к тому, что проверили, а не к имени |
| Сертификат цели | ❌ нет | читается с `rejectUnauthorized:false`, валидность определяется по `authorizationError` |
| Заголовки ответа цели | ❌ нет | извлекается только `Server` и факт наличия 4 заголовков; значения не интерпретируются |
| Конфигурация (env) | ✅ да в пределах процесса | `PUBLIC_ORIGIN`, `TRUST_PROXY`, `DEMO_MODE`, `NODE_ENV`, `PORT` |

## 5. Ключевой инвариант SSRF-защиты

Схема держится на трёх шагах, и порядок здесь — часть защиты:

1. **Резолв**: `dns.lookup(hostname, { all: true })` — получаем **все** адреса.
2. **Проверка всех**: `if (!ips.every(isPublicIp)) return []` (`net-guard.js:63`) — если хотя бы один адрес не публичный, отказ целиком. Это защищает от «умного» DNS, который отдаёт публичный адрес для проверки и приватный для подключения.
3. **Подключение по проверенному IP**: `connectIp = resolvedIps[0]` (`server.js:150`), а hostname передаётся отдельно — в `Host` (`checks.js:90, 112`) и в SNI (`checks.js:39, 85`).

**Почему это закрывает DNS rebinding:** между «проверили» и «подключились» нет повторного резолва. Даже если домен сменит A-запись через секунду после проверки, соединение пойдёт на уже проверенный IP. Классическая уязвимость — «проверили имя, подключились по имени» — здесь устранена конструктивно.

**Классификация адреса** (`isPublicIp`, `net-guard.js:6-50`) построена как аллоулист: разрешено только `ipaddr.js.range() === "unicast"`. Всё остальное — приватное, loopback, link-local, CGNAT, ULA, multicast, 6to4, Teredo, NAT64 — блокируется по умолчанию. Нераспознанный ввод тоже блокируется (fail closed). Перед проверкой диапазона выполняются три разворачивания/исключения: IPv4-mapped любой формы (`:16-19`), NAT64 `64:ff9b::/96` с рекурсивной проверкой встроенного IPv4 (`:21-30`) и полный запрет устаревшего IPv4-compatible `::/96` (`:43-46`).

**Чего эта схема не закрывает:**

* **NAT64/DNS64 с нестандартным префиксом.** Фильтр по литералу видит «обычный публичный IPv6», а сеть за ним маппит его во внутренний IPv4. Лечится только сетевым egress-фильтром.
* **Любую цель, которая действительно публична.** Сканирование публичного чужого хоста защитой не блокируется — это вопрос назначения сервиса и правовой, а не технический.

## 6. Демо-режим и принцип fail-closed

`DEMO_MODE=true` разрешает обойти проверку и обратиться к `localhost` / `127.0.0.1` (`server.js:136-138`). Это единственная ветка, обходящая SSRF-фильтр, поэтому её включение защищено двумя условиями (`server.js:18-22`):

```
DEMO_MODE === "true"  И  NODE_ENV === "development"   →  работаем
иначе (если DEMO_MODE)                                 →  process.exit(1)
```

Логика специально инвертирована: раньше проверка была «если production — запретить», то есть при незаданном `NODE_ENV` (значение по умолчанию в любом голом окружении) демо-режим молча включался. Теперь «разрешено только при явно заданном development» — ошибка конфигурации не открывает доступ, а останавливает сервис. Формулировка «запрещено по умолчанию» — это и есть fail-closed.

## 7. Лимит частоты

```
rateKey(req.ip) → IPv4-mapped разворачивается до IPv4
                → IPv6 нормализуется до /64 (смена младших 64 бит не даёт нового окна)
                → невалидный адрес → общий бакет "unknown"
                    ↓
lastScan: Map<key, timestamp>   TTL = 10 с, чистка раз в 30 с, MAX_KEYS = 10 000
                                вытеснение — LRU (ключ при касании переносится в конец)
```

Лимит списывается **после** базовой валидации (`server.js:115-119`), поэтому мусорные тела и подделанное согласие окно не занимают. Вытеснение — LRU (`server.js:72-79`): активный ключ при обращении переносится в конец очереди и не выпадает первым. Невалидный адрес клиента не создаёт отдельный бакет, а попадает в общий `"unknown"` (`server.js:69`) — иначе смена `X-Forwarded-For` давала бы бесконечное число окон.

Смысл `/64`-нормализации: без неё клиент с одной IPv6-подсетью получает 2⁶⁴ бесплатных окон. С ней окно одно на подсеть — но, следовательно, **соседи по подсети делят его между собой** (осознанный компромисс).

Что лимит **не** обещает:

* не защищает от источника с выделенной `/48` (65 536 подсетей `/64`) или от ботнета;
* не является глобальным — карта живёт в памяти процесса, поэтому N реплик = N лимитов;
* не покрывает запросы, отвалившиеся на `hostRegex` (`server.js:131`): лимит списан на шаге 8, а имя проверяется на шаге 11, поэтому невалидный hostname всё ещё жжёт окно;
* уязвим к неверной настройке `TRUST_PROXY` — при `>0` без реального прокси значение `req.ip` приходит из заголовка, который контролирует клиент.

Для публичного развёртывания нужен внешний лимит (`express-rate-limit` + Redis), это прямо написано в README.

## 8. Обработка ошибок

Единый обработчик (`server.js:172-187`) — последний middleware перед `/healthz`. В нём: статус берётся из `err.status`/`err.statusCode`, в лог пишутся метод, путь и стек (`:176-177`), а наружу — дифференцированный текст (`:180-184`), чтобы 5xx не выдавалась за ошибку клиента. Через него проходят:

* ошибки `express.json()` — битый JSON (400), слишком большое тело (413);
* синхронные исключения маршрута;
* всё, что делает `next(err)`.

Наружу уходит только `{ error: <обобщённый текст> }` — без стека, без путей, без версий библиотек. Принципиальный момент: **это не зависит от `NODE_ENV`**. Раньше защита держалась на переменной окружения (не задал production — получил стек в ответе), теперь она работает всегда, а `NODE_ENV` влияет лишь на текст 404 от `finalhandler`.

Внутри маршрута свой `catch` логирует исключение и отдаёт обобщённый 500 (`server.js:166-169`). Диагностика при этом не потеряна: стек остаётся в серверном логе и не уходит клиенту. Остаточный путь утечки — `next(err)` при `res.headersSent` (`:178`): ошибку добирает `finalhandler`, который в не-production окружении умеет вернуть стек. Практически недостижимо, но именно поэтому `NODE_ENV=production` на проде всё ещё имеет смысл.

## 9. Фронтенд и CSP

* `API_URL = "/api"` — относительный путь. Поэтому одинаково работает `http://localhost:3000`, LAN-адрес и HTTPS за прокси, и не конфликтует с собственной политикой `default-src 'self'` (из которой наследуется `connect-src`).
* Рендер — **только** `textContent`. Причина не в аккуратности: в отчёт попадает `Server`-заголовок чужого сервера, то есть данные, контролируемые третьей стороной. `innerHTML` здесь был бы XSS.
* Обработчик кнопки вынесен из разметки в `script.js:100`, чтобы работал строгий `script-src 'self'` без `'unsafe-inline'`.
* `style-src` сужен до `'self'` — инлайновых стилей в разметке нет.
* Клиентский таймаут (30 с) реализован через `AbortController`, кнопка блокируется на время запроса.

## 10. Что сервер хранит и логирует

| Данные | Где | Срок жизни |
|---|---|---|
| IP клиента | `lastScan` (память) | ≤10 с, при переполнении вытесняется |
| IP клиента | `console.log` | навсегда — в stdout/логах процесса; ротации нет |
| hostname цели | `console.log` | то же |
| Результаты скана | только в HTTP-ответе | не сохраняются |
| Сертификаты, заголовки цели | только в ответе | не сохраняются |
| Секреты, токены, пароли | — | отсутствуют: внешних API проект не вызывает |

Ничего не пишется на диск. Единственное состояние процесса — `Map` со временами последних запросов.

При старте в лог попадает разрешённый origin (`server.js:195`) и, если включён демо-режим, соответствующая строка (`:196`). Это диагностика, а не секрет: origin и так виден в заголовках. Есть `/healthz` (`server.js:190`), который отдаёт `{ok, uptime}` — ничего сверх факта, что сервис жив.

## 11. Тестирование

Покрыто: `test/net-guard.test.js` — 20 адресов на блокировку (включая `::ffff:7f00:1`, `::127.0.0.1`, `64:ff9b::7f00:1`, `::7f00:1` и `::a9fe:a9fe`), 4 на разрешение и 5 мусорных на fail-closed. Ключевые развороты — mapped, NAT64 и запрет `::/96` — закреплены тестами, то есть ровно те адреса, которые закрывали дыры аудита v3, теперь защищены от регрессии. Классификация адресов — единственное решение, на котором держится SSRF-защита, и она проверяется без сети.

Не покрыто и почему:

| Что | Почему нет | Как закрыть |
|---|---|---|
| `resolvePublicIps` | `dns.lookup` вшит внутрь функции | инъекция резолвера: `resolvePublicIps(host, { lookup = dns.lookup } = {})` → три теста (все публичные / смесь / только IPv6) |
| `rateKey` | не экспортируется | экспорт + тесты на `/64`-группировку, IPv4-mapped и бакет `"unknown"` |
| `remember` / LRU-вытеснение | не экспортируется | вынести в модуль и проверить, что при переполнении вытесняется самый давно использованный ключ, а не самый старый по вставке |
| HTTP-слой (400 без стека, 429, CORS-заголовок) | `server.js` делает `process.exit()` и `app.listen()` при импорте — импортировать нельзя | разделить `src/app.js` (экспорт приложения) и `src/server.js` (env + listen) |
| `checks.js` | требует сети | `parseHeaders` — чистая функция, тестируется без сети |

## 12. Технический долг

| Долг | Влияние |
|---|---|
| `server.js` выполняет `process.exit()` (`:15`, `:21`) и `app.listen()` (`:193`) при загрузке | HTTP-слой непокрываем тестами (см. §11) |
| Конфигурация размазана (`:9-16`, `:18`, `:27`, `:192`) | нет единой валидации env; `PORT=abc` уйдёт в `listen("abc")` и создаст unix-socket вместо порта |
| `PUBLIC_ORIGIN` валидируется как URL, но не как http(s)-origin | `PUBLIC_ORIGIN=localhost:3000` (без схемы) парсится как URL со схемой `localhost`, `.origin` даёт строку `"null"`, CORS молча перестаёт работать. Лечится проверкой `if (PUBLIC_ORIGIN === "null") exit(1)` |
| Лог пишется **до** `hostRegex` (`:129` против `:131`) | лог-инъекция сейчас не exploitable (парсер URL убирает переводы строк и ограничивает длину), но это регрессия SEC-10: защитный порядок восстановлен не был |
| Дублирующийся блок NAT64 в `net-guard.js` (`:21-30` и `:32-41`) | мёртвый код: второй блок недостижим, читателю непонятно, какая проверка настоящая |
| Нет потолка одновременных сканов | при обходе лимита — исчерпание дескрипторов; частично сглажено тем, что лимит срабатывает до сети |
| Express 4 | самая свежая в линии 4.x и получает патчи; переход на 5.x — отдельная задача |
| Нет `engines`, `private: true` в `package.json` | случайный `npm publish`; расхождение версий Node между локалью и CI |

## 13. Модель угроз (кратко)

| Угроза | Контроль | Остаток |
|---|---|---|
| SSRF к внутренней сети / metadata | резолв + проверка всех IP + подключение по IP; запрет `::/96` | NAT64/DNS64 с нестандартным префиксом |
| DNS rebinding | подключение по проверенному IP, без повторного резолва | — |
| XSS через данные цели | `textContent`, строгий CSP, вынесенный обработчик | — |
| Утечка внутренней информации через ошибки | единый error handler, JSON без деталей, стек только в серверный лог | `next(err)` при `headersSent` → `finalhandler` (в dev вернёт стек) |
| Подмена `X-Forwarded-For` при неверном `TRUST_PROXY` | невалидные значения схлопываются в общий бакет `"unknown"`, IPv6 — в `/64` | включать `TRUST_PROXY` только за реальным прокси |
| Использование сервиса третьими лицами | CORS по origin, лимит частоты, согласие, DISCLAIMER | распределённый источник; нет проверки владения доменом |
